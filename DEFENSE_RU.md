# Как объяснить Visitor на защите

На доске два вида заданий: охота и доставка. Персонажу нужен журнал с инструкциями, а для выбора заданий полезно знать общую награду. Поэтому данные хранятся в заданиях, а каждую операцию выполняет отдельный посетитель.

**Двойная диспетчеризация на примере доставки:**

1. В цикле переменная `quest` имеет тип `Quest`, но внутри неё объект `DeliveryQuest`. При вызове `quest.accept(visitor)` Java выбирает реализацию `DeliveryQuest.accept`.
2. Там написано `visitor.visitDelivery(this)`. Здесь `this` — конкретная доставка. Имя метода уже задано кодом; во время выполнения Java выбирает его реализацию по объекту посетителя. Если посетитель — `RewardVisitor`, он прибавляет к сумме 3 монеты за каждый километр. Если это `JournalVisitor`, он печатает предмет, место и расстояние.

**Проверка на бумаге.** Четыре паука дают 40 монет, доставка на 6 км — 18, два волка — 20. Итого 78. На пустой доске новый посетитель наград вернёт 0. Для нового независимого подсчёта создаём новый `RewardVisitor`: повторный обход тем же объектом добавит награды ещё раз.

**Что проще расширить?** Для подсчёта заданий добавлен только новый посетитель и отдельный пример запуска. Но если появится рыбалка, придётся добавить `visitFishing` в интерфейс и реализовать его у каждого посетителя. Поэтому Visitor подходит, когда виды заданий стабильны, а операции меняются.

**Отличие от Strategy из задания 5.** Там мы меняли правило решения одной задачи: как поделить золото. Здесь у одной коллекции заданий несколько разных операций: вывести журнал, посчитать награду, посчитать задания по видам.
